# Experiment 0.1a — Provider-call diagnostics

## Motivation

This follow-up implements [GitHub issue #5](https://github.com/Talref/Story-Kernel/issues/5).
It makes provider behavior falsifiable without making provider wire formats or raw payloads part of
the semantic conversation.

## Trace shape

Every provider call made during a runtime turn creates a compact record linked to that turn's
execution. It records the provider and selected model, one-based call index, operation, HTTP status,
response ID/model, finish reason, whether any provider action fields were present, normalized tool
names/count, latency, usage, adapter warnings or errors, and routing metadata only when the provider
returned it.

The call index makes a tool round trip visible as multiple provider calls under one execution. The
diagnostics deliberately distinguish:

- a normal text response with no action fields;
- a response containing an action field the adapter did not normalize;
- an adapter parse failure;
- an HTTP or upstream failure.

Only structured `tool_calls` accepted by the adapter become runtime tool calls. Prose and unfamiliar
action fields are never interpreted as tools.

## Raw payload artifacts

Raw request and response bodies are stored in a separate table, not embedded in the normal execution
summary. Capture is enabled by default for this development experiment. Set
`STORY_KERNEL_CAPTURE_PROVIDER_PAYLOADS=false` (also accepts `0`, `no`, or `off`) to disable it, or
pass `capture_raw_provider_payloads=False` when constructing the harness/runtime in code.

Before persistence and display, nested authorization/API-key/cookie/credential fields, bearer-token
strings, and the configured NanoGPT key are redacted. Request headers are not captured by the
NanoGPT adapter.

The Gradio **Execution trace** tab always shows compact summaries. Its collapsed **Raw provider
payloads** section loads raw artifacts only on request and can clear every raw artifact without
removing conversations, world state, executions, or their compact call summaries. Experiment export
keeps compact calls and raw artifacts separate under `provider_diagnostics` and applies the same
redaction.

## Failure semantics

Provider/runtime failures are recorded as execution and provider-call errors and surfaced in the UI
status. The attempted user message is retained, but no synthetic assistant error is appended to the
conversation. Later provider requests therefore never receive infrastructure failures as if the
model had said them. Successful assistant responses still persist normally.

## Verification

Deterministic tests cover successful text and tool responses, multi-round indexing, unknown action
fields, adapter and HTTP failures, raw-capture configuration, redaction, independent raw clearing,
and UI conversation semantics.

For the manual issue scenario, select `deepseek-chat`, ask a Hogwarts/houses question that encourages
a tool call, then inspect the compact calls in **Execution trace**. Confirm the selected and returned
models, finish reasons, raw-action indicator, normalized tool names/count, latency, usage, and any
provider routing metadata. Open raw payloads only when wire-level diagnosis is required, then clear
them and confirm that the compact trace remains.
