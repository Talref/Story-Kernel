# Experiment 0.1a — Conversation Continuity Touches

## Motivation

Follow-up implementation for [GitHub issue #3](https://github.com/Talref/Story-Kernel/issues/3).

The original Gradio surface persisted conversation records but kept the active conversation and
selected model only in ephemeral Gradio state. A browser refresh therefore presented an empty chat,
which obscured the persistence behavior Experiment 0.1a is intended to inspect.

## Persisted UI state

The application-state store now records two non-world preferences:

- the active conversation ID;
- the selected model for the next conversation.

These preferences live outside A. **Reset world** does not alter them. Experiment export/import
includes them under `application.ui_preferences`, and import verifies that an active-conversation
preference refers to an included conversation.

On page load or application restart, the harness:

1. refreshes the current NanoGPT subscription model list;
2. loads the persisted conversation index;
3. restores the last active conversation, if present;
4. restores its stored transcript;
5. sets the model control to that conversation's immutable pinned model.

If there is no conversation, the most recently selected model is restored for creation of the first
or next conversation. A saved model remains selectable even when a transient model-list request
fails or the model no longer appears in the current provider response.

## Conversation browser

The **Previous conversations** selector lists persisted conversations by creation time, exact model,
and a short ID suffix. Selecting one restores its transcript and pinned model, marks it active, and
loads its execution trace. Resuming it continues to use the recorded model even if another model was
previously visible in the selector.

Selecting another model while a conversation is open saves that choice for **New conversation**; it
does not mutate the active conversation's model.

## Staged chat rendering

Sending now uses two UI callbacks:

1. validate/create the conversation, clear the input, and append the user message to the visible
   chat immediately;
2. invoke the model runtime and append its eventual assistant response.

World and execution inspectors refresh after the second stage. The runtime remains responsible for
persisting the complete user/assistant turn, so the visual staging does not create a second transcript
authority.

## Verification focus

Automated tests recreate the complete harness over the same SQLite path to cover actual restart
behavior. They also cover browsing older conversations, pinned-model restoration, pre-conversation
model restoration, world-reset independence, preference export/import, and proof that staged user
rendering occurs before the fake provider is invoked.
